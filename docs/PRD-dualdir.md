# SnapNote v1.6.0 更新机制重构 PRD——双目录原子切换

> 版本：v1.6.0（架构重构版）
> 日期：2026-10-05
> 状态：**待确认**（确认后开工）
> 决策背景：用户拍板方案 A（先立地基，浏览器扩展二期顺延至 v1.7.0）
> 前置分析：v1.5.x 更新链路七连修复盘（详见 2026-10-04 工作记录）

---

## 一、一句话目标

把更新机制从「程序退出后由外部脚本删旧拷新（危险、不可测、环境依赖）」重构为
「新版本完整就位后翻指针（安全、可测、环境无关）」——从源头消灭 tar 劫持、
robocopy 中断、杀软拦截这一整类故障，让以后每个版本的发布都不再是赌注。

## 二、为什么必须重构（结论复述）

v1.5.x 替换链的结构性缺陷，补丁无法收敛：

| 证据 | 说明 |
|------|------|
| 5/7 版本在修同一条链路 | 同一子系统反复出问题 = 结构问题而非实现问题 |
| 失败空间无限 vs 测试空间有限 | PS 脚本跑在用户环境全集里（PATH/杀软/盘符/权限），CI 只能模拟有限环境 |
| 破坏性语义 | robocopy /MIR 先删后拷，任何中途死亡 = 目录半损 |
| 两个成熟度对照组 | Chrome/Steam 均为「双目录+指针」；无主流软件以「退出后脚本镜像替换」为唯一更新路径 |

v1.5.5 的多层防御（绝对路径 tar、兜底解压、回滚、留痕）把**已知**坑埋了，
但「不再踩新坑」无法被证明。本 PRD 消灭的是坑的**类别**。

## 三、新架构总览

### 3.1 目录布局

```
E:\project\SnapNote\              ← 用户解压/安装的根目录（双击入口永远在这层）
├── SnapNote.exe                  ← 启动器（极薄 stub，~10KB，逻辑永不变化）
├── channels.json                 ← 指针文件：{"current":"app-1.6.0","previous":null}
├── app-1.6.0\                    ← 版本目录 A（当前运行）
│   ├── SnapNoteApp.exe           ← 主程序（v1.6.0 起由 SnapNote.exe 改名，原因见决策 1）
│   ├── resources\                ← Electron 资源（asar 等）
│   └── ...（locales、dll 等）
└── app-1.7.0\                    ← 版本目录 B（更新就位后存在；A 变为回滚后路）
```

### 3.2 角色职责

| 角色 | 形态 | 职责 | 更新频率 |
|------|------|------|----------|
| 启动器 SnapNote.exe | C# 编译的 Win GUI stub（源码入仓库，CI 编译） | 读 channels.json → 拉起 current 目录主程序；指针损坏时自动扫 app-* 取最大版本兜底；全损时弹窗提示重新下载 | **永不更新**（逻辑固定） |
| 主程序 SnapNoteApp.exe | Electron 应用（现有一切功能） | 便签/收集/气泡/更新器宿主；更新器全程 Node 代码 | 每版本 |
| channels.json | 纯文本指针 | current/previous 两个版本目录名 | 每次更新翻转 |
| 用户数据 | %AppData%\SnapNote（现状不变） | 便签、备忘录、设置 | — |

## 四、四条关键链路设计

### 4.1 全新安装（首次用户）

下载 zip（新布局成品）→ 解压到任意目录 → 双击根 `SnapNote.exe`（启动器）→
启动器读 channels.json → 拉起 `app-1.6.0\SnapNoteApp.exe`。**解压即用，
与现状体验完全一致。**

### 4.2 常规更新（v1.6.0+ 客户端，核心链路，100% Node）

```
检查更新（不变）→ 下载 zip + sha256 校验（不变，27 个测试继续护住）
→ 【新】applyUpdate（全 Node，可单测）：
     1. 系统 bsdtar 绝对路径解压 zip 到临时目录（失败无害，可重试，不碰根布局）
     2. 定位 zip 内 app-x.y.z\ 目录 → 挪入根目录（同卷 rename 原子；跨卷 copy+校验+删源）
     3. 写 channels.json：current=新版本，previous=旧版本
        （先写临时文件再 rename，保证指针翻转原子性）
     4. 托盘通知「新版本已就绪，点击重启生效」——不自动杀程序（主动权在用户）
→ 用户点「重启进新版」→ spawn app-x.y.z\SnapNoteApp.exe → 本进程退出
→ 新版本首跑：异步清理 previous 目录 + 临时残留 + update-error.log
```

**失败语义**：上述任何一步失败 = 旧版本原地照跑，指针未翻，用户零感知损失。
最坏情况是「这次更新没成」，而不是旧版任何形式的损坏。

### 4.3 v1.5.x → v1.6.0 迁移（旧 PS 链最后一跑，接力式迁移）

现有 v1.5.5 客户端执行**未修改的** PS 脚本对新布局 zip，推演已逐行验证成立：

| PS 步骤 | 对新 zip 的执行结果 |
|---------|---------------------|
| 等待旧进程退出 | Get-Process SnapNote ✓（旧真程序名未变） |
| System32 tar 解压 | 产出 {SnapNote.exe(启动器), channels.json, app-1.6.0\SnapNoteApp.exe + resources} |
| robocopy /MIR /XF SnapNote.exe | app-1.6.0\ 整体镜像入根 ✓（主程序已改名 SnapNoteApp，**不触发** /XF 对同名文件的深层排除——这是改名的根本原因）；根目录启动器被 /XF 跳过，由下一步补 |
| exe 两步换名 | 旧根 SnapNote.exe → .old；从解压目录拷 SnapNote.exe（启动器）→ 根 ✓ |
| 启动根 exe | =启动器 → 读 channels.json → 拉起 app-1.6.0\SnapNoteApp.exe ✓ |
| 新程序首跑 | cleanupStale 删 .old（v1.5.5 已有）✓ 迁移完成 |

**旧链一次都不用改，跑完即完成新布局铺设**；此后该客户端永久转入 4.2 纯 Node 链路。
v1.6.0 起代码中删除 PS 生成逻辑（git 历史里永久可回溯）。

### 4.4 回滚（用户主动权）

托盘菜单新增「回滚到上一版本」：channels.json 的 current/previous 翻转 →
经启动器拉起 previous 版本 → 通知「已回滚至 vX.Y.Z」。任何一次更新后
不满意，用户 10 秒内可退回，无需联系开发者。

## 五、关键决策与取舍（已推演，可推翻）

| # | 决策 | 理由 | 代价 |
|---|------|------|------|
| 1 | 主程序 exe 改名 SnapNoteApp.exe | 旧 PS 的 /XF 按文件名匹配会深层排除子目录内同名 exe；改名后 4.3 接力迁移才能零修改成立 | 任务管理器进程名显示为 SnapNoteApp（轻微体验损失） |
| 2 | 启动器用 C# stub（CI 上 csc 编译，.NET Framework 4.x，Windows 自带运行时） | 极薄（<100 行）、秒启动、无 Electron 负担；源码入仓库随 CI 编译，不引入新构建依赖 | 仓库新增 launcher.cs；本地 Linux 无法编译它（由 CI 负责，不影响开发流） |
| 3 | 解压暂用系统 bsdtar 绝对路径（v1.5.5 逻辑复用），失败重试无害 | 零新依赖；失败语义已从「致命」降级为「可重试」 | 环境依赖残留一项（列入 v1.7 优化：换纯 JS 解压彻底归零） |
| 4 | 保留 previous 一层版本目录 | 回滚能力的物理基础 | 磁盘 ~2× 版本目录（约 600-700MB）；托盘提供「清理旧版本」入口 |
| 5 | 更新就绪后不自动重启 | 用户产品观：主动权交到用户手里 | 无（通知+菜单高亮引导） |

## 六、测试与验收标准

### 6.1 自动化（CI 必须全绿才发版）

- **新增单测 ~15 个**：指针翻转原子性、双目录就位、跨卷拷贝分支、回滚翻转、
  新程序首跑清理、迁移识别（app-* 目录/平铺布局判定）、启动器目标推导的
  Node 侧同构逻辑
- **e2e_update.js 重写为双目录版**：CI 真实跑「v1.6.0 → v1.6.1」全链
  （下载→解压→指针→重启→新版本自检）——**预期首次绿**（不再有 PS 环境依赖）
- 冒烟改为启动器链：launcher → SnapNoteApp --smoke-test

### 6.2 真机验收（两跳，缺一不可）

1. **迁移跳**：v1.5.5 真机点「重启并更新」升 v1.6.0 → 重开后 `E:\project\SnapNote`
   出现启动器+app-1.6.0 子目录 → 版本号显示 1.6.0 ✓（这条同时验证了 v1.5.5
   的 PS 修复，一箭双雕）
2. **Node 链跳**：随即发布 v1.6.1（小改或纯版本迭代）→ 真机从 1.6.0 走纯
   Node 更新到 1.6.1 → 成功后回滚菜单可退回 1.6.0 ✓

### 6.3 验收即结案

两跳通过后，更新机制从「每次发布的赌注」转为「有测试护城河的常规代码」。

## 七、风险清单与兜底

| 风险 | 概率 | 兜底 |
|------|------|------|
| 启动器被 SmartScreen/杀软误报（小体积未签名 exe） | 低 | 与现状 zip 解压 exe 同属 MotW 场景，非新增类别；误报反馈率极低时再评估签名 |
| E 盘特殊文件系统 rename 非原子 | 低 | 指针写入用「临时文件+替换」双保险；失败重试无害 |
| 迁移跳失败（PS 链最后一次跑挂） | 低（v1.5.5 已多层防御） | 失败=停留 v1.5.5，无损；update-error.log 留痕；可手动下载 v1.6.0 zip 解压覆盖（全新布局兼容） |
| 启动器自身需要更新的极端场景 | 极低（逻辑永不变化） | 兜底=随版本目录分发新启动器副本，Node 链在翻转指针前同步替换根启动器（作为附加步骤，非主路径） |
